# Bugfix: дубли отметок «Близость» и отсутствие истории

Статус: ✅ реализовано (2026-10-21), evidence в `tasks.md`
Дата: 2026-10-19
Проект: `cycle-bot` (aiogram 3, SQLite + Postgres)
Тип: Bugfix + Quick Spec (правка < 1 дня)

## Источник

Отзыв клиентки (скриншоты переписки от 2026-10-19, 13:18):

1. Карточка «БЛИЗОСТЬ» показывает `18 октября · С защитой` **дважды**.
   Клиентка: «и 18 случайно два раза отметила».
2. На вопрос «как предыдущие посмотреть» бот отвечает невпопаду:
   «а сю было» / «вот я и не помню 6-8».
   То есть older-записи (6–8) клиентка знает, что они есть, но достать их не может.

## Current behavior (что происходит сейчас)

| # | Поведение | Место |
|---|-----------|-------|
| C1 | `add_sex` делает голый `INSERT` в `sex_logs` без проверки уже существующей записи на этот день | `app/db.py:493` |
| C2 | На `sex_logs` нет `UNIQUE (user_id, day)` — дубль физически возможен | `app/db.py:41` |
| C3 | `recent_sex(limit=8)` возвращает 8 строк, `sex_card` печатает `rows[:5]` | `app/db.py:502`, `app/texts.py:260` |
| C4 | Пагинации нет вообще: кнопки «показать ещё» не существует, потолок — 5 записей | `app/keyboards.py:139` (`sex_when_kb`) |
| C5 | Нет ответа на естественный вопрос пользователя — бот молчит на свободный текст | `app/handlers.py:943` |

**Root cause:** отметка близости реализована как «append-only журнал», где один день =
одна строка, но ограничение «один день = одна строка» нигде не выражено — ни в схеме,
ни в коде. Двойной тап по кнопке «С защитой» (или повторный заход через «Другая дата»)
даёт два `INSERT`. Второй корень — фича «история близости» никогда не была сделана,
карточка показывает только срез.

## Expected behavior (что должно быть)

- Повторная отметка того же дня **не создаёт дубль**, а обновляет существующую запись
  (например, сменила «С защитой» → «Без защиты»).
- В карточке «Близость» всегда **одна строка на день**, даже если в базе исторически
  остались дубли (backfill без миграции, на уровне чтения).
- Полная история доступна: кнопка «Вся история» + постраничный показ (по 5) с «Показать ещё».
- Ошибочную отметку можно **отменить** (удалить запись за конкретный день).
- Бот отвечает на «как посмотреть предыдущие» подсказкой с кнопкой, а не молчит.

## Unchanged behavior (что НЕ трогаем)

- Схема `sex_logs` и все таблицы остаются **без изменений**: никаких `DROP`, `DELETE`,
  `ALTER`, никакого пересоздания. Старые строки остаются как есть.
- Расчёт цикла, голубые дни, красные дни, задержка, дневник, партнёр, уведомления — без изменений.
- Telegram-партнёру уходит то же самое сообщение о близости, что и раньше.
- Приватность `share_sex` работает как раньше: скрыта — не показываем и не отправляем.

## Ограничения (жёсткие)

- **L1. Данные не теряются ни при каких обстоятельствах.** Правка — только чтение и
  `UPDATE`/`INSERT`; ни одной операции, удаляющей строку из `sex_logs` по починенной логике.
  Единственная `DELETE`-подобная операция — явная отмена отметки **по нажатию самой пользовательницы**.
- **L2. Никаких миграций схемы.** Исторические дубли не чистим массово — гасим на чтении.
- **L3. Работает на обоих хранилищах** (SQLite и Postgres через `DATABASE_URL`).
- **L4. Бэкап перед запуском.** Локальная `luna.db` уже скопирована в `backup/luna-20261019-133628.db`
  (SHA256 сверен). Перед деплоем на прод — обязательный `pg_dump` на стороне Render.

## Acceptance criteria

- **AC-1.** Два нажатия «С защитой» за один день → в `recent_sex` одна строка за этот день.
- **AC-2.** Смена типа защиты за тот же день обновляет запись, а не добавляет новую.
- **AC-3.** Если в базе лежат два дубля за 18 октября, карточка «Близость» показывает
  **одну** строку 18 октября (последнюю по `id`).
- **AC-4.** Кнопка «Вся история» открывает список по 5 записей; «Показать ещё» листает дальше;
  на последней странице кнопки листания нет.
- **AC-5.** Кнопка «Отменить отметку» на конкретной записи удаляет её и возвращает карточку.
- **AC-6.** Текст «как посмотреть предыдущие» (регистронезависимо, в т.ч. «посмотреть»/«смотреть»)

- **AC-7.** При `share_sex = 0` история близости партнёру не уходит и не показывается в карточке партнёра.
- **AC-8.** `pytest` зелёный, добавлены тесты на: отсутствие дубля при повторе, схлопывание
  исторических дублей на чтении, пагинацию, отмену отметки.

## Риски

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| Схлопывание дублей на чтении скроет «лишнюю» строку из истории | Низкая | Берём последнюю по `id` — это и есть финальная воля пользователя; сами строки остаются в базе |
| `SELECT ... GROUP BY` на больших объёмах | Низкая | Индекс по `(user_id, day, id)`; на текущем объёме (десятки записей) нерелевантно |
| Изменение текста карточки сломает ожидания клиентов | Средняя | Правка аддитивная: старые блоки остаются, добавляется блок навигации |
| Прод-деплой затронет живой Postgres | Средняя | Перед деплоем `pg_dump`; миграций нет — только код |

## Решение об архитектуре (D1)

**D1. Не добавляем `UNIQUE (user_id, day)` и не чистим дубли в базе.**

Почему: на проде уже есть дубли (18 октября ×2). `CREATE UNIQUE INDEX` на такой таблице
упал бы с ошибкой на старте — бот не поднялся бы вообще. Массовый `DELETE` старых дублей —
это операция, удаляющая пользовательские данные, чего мы избегаем (L1/L2).

Альтернативы, отклонённые:
- «Чистка дублей миграцией» — отвергнута: удаляет данные, риск для прода.
- «Оставить двойной тап как есть» — отвергнута: это и есть жалоба клиента.
- `ON CONFLICT DO UPDATE` через уникальный индекс — отвергнута по той же причине (нужен индекс).

Следствие: инвариант «один день = одна запись» обеспечивается на уровне приложения
(`add_sex` → `UPDATE` если день есть, иначе `INSERT`) плюс схлопывание на чтении.
Схема остаётся совместимой с уже существующими дублями.
