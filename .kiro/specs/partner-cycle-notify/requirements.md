# Requirements — partner-cycle-notify

## Intent

Партнёр по приглашению должен получать полный поток событий владелицы цикла: каждый день отмеченных красных дней (день 1, день 2, день 3 … по всей длине периода), плюс близость без условий, задержка, голубые дни, «завтра красные». Сейчас партнёр получает максимум день 1 красных, а близость молча теряется из-за флага `share_sex`.

## Boundaries

- Файлы — только `app/` (+ тесты `tests/`). Не трогать: `luna.db`, `luna.db-shm/wal`, `*.bak`, `.env`, схему БД (никаких ALTER/миграций).
- Деплой — через существующий `deploy/update.sh` (он делает бэкап `luna.db`); никаких прямых правок на сервере.
- Поведение для самой владелицы не меняется (её уведомления остаются как были).

## Functional Requirements

### FR-1: Каждый день красных — партнёру
WHILE у владельца активны красные дни (phase = period) AND день ≥ 2
THEN система ЕЖЕДНЕВНО (в ежедневный час владельца, `notify_hour`) шлёт партнеру уведомление «Красные дни · день N» (N = число дней от старта красных).

### FR-2: День 1 — уже есть, не дублируем
Моментальный пинг «начались красные дни» и дневной `red_today` на день 1 сохраняются как есть; новый блок (FR-1) не шлёт второе сообщение на день 1 (условие day ≥ 2).

### FR-3: Близость — всегда партнёру
WHEN владелица отмечает близость
THEN партнёр получает уведомление независимо от значения `share_sex` (гейт в `ping_viewers` снят). Флаг остаётся в БД (схему не меняем), но перестаёт управлять доставкой.

### FR-4: Моментальный пинг при каждой отметке красных
WHEN владелица ставит/переносит красные дни (любой путь: `set_period`, `revise_period`, ветка «цикл собран»)
THEN партнёр получает моментальное уведомление «У {name} начались красные дни» — не только через путь `nxtd`.

### FR-5: Остальные события партнёру — сохраняются
Задержка (1й и 7й день), голубые дни, «завтра красные» — партнёр продолжает получать без регрессий.

### FR-6: Аудит мелких багов в потоке уведомлений
Задача аудита: пройти весь notify-поток (ping_viewers, daily_tick, пути отметок) и починить найденное в рамках этой спеки (зафиксированные кандидаты: пинги на путях 670/691 в handlers.py, семантика `share_sex` после снятия гейта — UI не должен врать).

## Non-Functional Requirements

### NFR-1: Схема и данные БД — неприкосновенны
Никаких ALTER/CREATE/DROP; новые kind-строки (`red_dayN`) пишутся в существующую `notify_sent` (dedup по user+kind+date). Перед деплоем — обязательный бэкап `luna.db` (уже есть в `update.sh`, проверяем факт).

### NFR-2: Тесты зелёные
`pytest` проходит до деплоя; новые тесты для day-N и снятого гейта.

### NFR-3: Минимальный дифф
Изменения только в `app/notify.py`, `app/handlers.py`, `app/texts.py`, `app/keyboards.py` (кнопка toggle, UI не должен врать) + тесты.

## Acceptance Criteria

- AC-1: she sets 5 day red window → partner receives: instant «начались» в момент отметки + «день 2», «день 3», «день 4», «день 5» в её notify_hour; день 1 мгновенно, без дублей.
- AC-2: share_sex = 0 → партнёр всё равно получает пинг близости.
- AC-3: Отметка красных через альтернативный путь («цикл собран») тоже отправляет моментальный пинг партнёру.
- AC-4: `pytest` зелёный; `notify_sent` набито одним видом kind на день (нет дублей при перезапуске тика).
- AC-5: Деплой на сервер: бэкап `luna.db` существует, PM2 онлайн, схема таблиц не изменилась (сравнение PRAGMA table_info до/после).
